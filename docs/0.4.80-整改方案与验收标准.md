# 听见 0.4.80 整改方案与验收标准

基线为 GitHub `main` 上的 0.4.80 实现。编号对应《听见 0.4.80 优化清单》。这一轮先修复可以定位到代码的行为，并用小规模回归覆盖原来漏测的边界。

## 第一轮

| 编号 | 整改 | 验收标准 |
| --- | --- | --- |
| 1、6 | 统一正式识别与预览的语种判定。结合模型标签和文字里的语种证据，必要时只对可信候选补做一次正式识别。 | 中英夹杂句走正确方向。英文仍走英文侧，日语假名和韩文保持各自方向。无语音、纯语气词和已知背景幻听不会因放宽语种条件而出字。无可靠候选时保留已经显示的可读内容。 |
| 2 | 长段靠近上限时优先找近期停顿，切点后的采样交给下一段。 | 自动测试用带编号的采样验证音频边界无漏样、无重复。用连续新闻复听，检查句首、句尾，以及上一段译文有没有进入下一段。 |
| 3 | 本机和云端的正式识别都优先于新预览。 | 已排队的正式识别前没有新预览插队。已经显示的原文或译文一直可读，正式结果能接续更新。 |
| 4 | 移除 POSIX 崩溃信号中的 Swift 和文件操作，交由 iOS 处理信号。 | 代码里不再注册这类信号处理器。调试包的崩溃由 iOS 留下原生诊断。重启后仍能读取旧版已留下的诊断和内存标记。 |
| 12 | 云端识别和翻译各使用一个总截止时间，限制 429／503 退避重试。正式识别按音频长短共用 22–42 秒，正式翻译共用 35 秒。已发出的推理读取超时后结束当前请求。 | 模拟连接失败可走备用地址，模拟 503 可短暂重试，模拟 Windows 接收请求后迟迟不响应时，同一句推理不再反复发送，队列继续处理后续句子，已有译文保留。 |
| 14 | 内存警告先回收本机声音克隆和说话人资源。暂用系统声音，初始阈值为回收后剩余不足 450 MB 或 8 秒内再次收到警告时，暂停核心本机模型。 | 连续内存警告只启动一份回收流程。轻度压力下仍能收录后续句子，严重压力下可提示用户重新开始。已有历史和磁盘音频仍能读取。结合真机日志验证阈值。 |
| 15 | 麦克风启动和重试移到音频队列，使用启动令牌拦截过时结果。 | 麦克风不可用时页面仍能响应。启动中再点停止或换模式后不会迟到开麦。实时翻译和对话翻译均保持单点操作。 |
| 22 | 在现有回归中补断句、语种、静音和回退边界，建立真机录音验收表。 | GitHub 的两条 iOS 工作流都能运行这些用例。真机复测覆盖下表，并附设备、模式及运行日志。 |
| 25 | 仅对有持续信号的克隆音频做有限增益。 | 近静音、孤立点击声、无效采样不会被当成正常朗读。正常音频无削波，低音量增益有明确上限。 |

## 真机和 Windows 验收

| 场景 | 操作与通过条件 |
| --- | --- |
| 静音和短句 | iPhone 16 Pro Max，在安静环境保持录音 60 秒，然后加入风扇、键盘声和两句轻声短句。无人说话阶段不产生句子，两条短句能出原文。 |
| 语种和断句 | 本机 SenseVoice 测普通中文、英语、中英夹杂、日语和韩语。用 30 秒以上连续新闻检查自然断句。补测「明天 meeting 讨论 API design」以及跨段的 `mid / west`。 |
| 译文接续 | 本机和云端各跑一轮。出预览后等待正式结果，确认等待、失败和修正期间已有译文保留，新段译文只对应本段。 |
| 云端异常 | Windows 模拟 503 和请求已接收但无响应。核对 App 与服务端日志，确认请求次数、总等待上限和后续句子恢复。 |
| 内存与启动 | 本机 SenseVoice、Hy-MT、ZipVoice 一起运行。用 Xcode 模拟一次及连续两次内存警告，记录是否继续收音。再测试蓝牙路由变更、启动中停止和对话模式切换。 |
| 声音 | 用正常、极轻、有静音边缘和只含点击声的克隆输出测试自动朗读与手动播放。播放开始和结束时声音图标应与实际状态一致。 |

后续按上一轮复核结论安排第 5、13、16、20、21、26、27 项。其余先采集性能和准确率数据，或暂缓表中的增模型方案。上下文继续以当前段为翻译输入，任何新做法都先通过上一段复述的回归用例。
